## 2. `PF-A4` 的 p95 为什么判不了（如实说明）

10 个有效样本呈**双峰**：8 个落在 544.7–605.4 ms，2 个落在 1523.5 / 1595.7 ms。

- p50 = 576.2 ms → 通过，且优于旧版基线（1136.3 ms）约 2 倍。
- p95 = 1595.7 ms → 按判据不通过。

**这 2 个慢样本归因于测量期间的外部负载**：用户当时在本机玩游戏（已确认）。它属于[11 §3](11-ACCEPTANCE.md)"测量口径"要排除的干扰，而不是实现问题——连续 6 次无外部负载的复测全部落在 524–696 ms，未再出现慢样本。

**因此本文不给出"p95 通过/不通过"的最终结论**，只记录事实：**需在无外部负载时复测**（建议 n ≥ 20，因为 n=10 时 p95 就等于最大值，单样本即可决定判定）。

> **一条方法论提醒**：小样本下 p95 极其脆弱——10 个样本时 p95 就是 max。判 `PF-A4` 的 p95 至少需要 n ≥ 20，并在测量期间独占机器。

## 4. 测量方法（可复现）

| 项 | 做法 |
| --- | --- |
| 冷启动口径 | 与 [baseline.md §4](baseline.md) 一致：**从进程创建**到主窗口出现**且响应 `WM_NULL`**（`SMTO_ABORTIFHUNG`）；**丢弃第 1 次样本**；每轮前杀干净残留 |
| 进程树 | 从宿主 PID 递归取子孙，**含全部 `msedgewebview2.exe`**（实测一个窗口 = 7 个进程） |
| 内存口径 | **私有工作集**（`Win32_PerfFormattedData_PerfProc_Process` 的 `WorkingSetPrivate`）逐进程求和——**不用工作集求和**（[11 §3](11-ACCEPTANCE.md) 的"内存口径"：多进程下共享页会被重复计算，实测 330.1 MB vs 78.9 MB） |
| 句柄口径 | 分两类（[11 §3](11-ACCEPTANCE.md) 的"句柄口径"）：自有进程取绝对值，WebView2 取增长 |
| CPU 口径 | 完整进程树 `TotalProcessorTime` 的 `ΔCPU秒 / Δt`（单核百分比） |
| 进程存活 | 每个样本前断言宿主仍在；**消失即判测量失败**，绝不允许记成"0% CPU / 0 句柄"（[baseline.md §4](baseline.md)） |
| 启动方式 | 经 WMI `Win32_Process.Create` 启动，使被测进程**脱离测量脚本自身的进程树**——否则会话级清理会中途杀掉它（这是本项目实际踩过的坑） |

| 门禁 | 状态 |
