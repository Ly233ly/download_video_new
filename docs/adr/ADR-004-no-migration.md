# ADR-004 · 数据不迁移，新库从 v1 开始

- **状态**：已接受
- **相关**：[03 数据规格](../03-DATA.md)、[10 §2](../10-DISTRIBUTION.md)

## 背景

旧实现使用 SQLite，结构版本 `6`，共 9 张表，迁移链为 v1→v6。迁移中包含若干**业务语义修复**（如 v2 把 `waiting_source` 改写为 `queued`、v3 修复误标重复、v5 把在途下载置为需重建）。

第一版重写文档计划演进到 v7 并保留完整迁移链语义。这带来三个问题：

1. 需要为每一代迁移写函数与测试，工作量与风险都不小
2. 升级回滚时需要保证数据库也能回滚——否则旧程序读不了已迁移的库
3. 迁移算法要求"确定性的完整算法"，包括空库、v1–v5、越界枚举映射等分支

**独立审查已把这三条列为最高优先级风险。**

## 决策

**新库结构版本为 `1`，不做任何历史数据迁移。**

| 项 | 决定 |
| --- | --- |
| 表数量 | **5 张**（旧 9 张） |
| 迁移链 | 无 |
| 旧数据库 | **不读取、不删除**，保留在用户数据目录 |
| 升级回滚 | 不涉及数据库事务——因为新版从不修改旧库 |

## 理由

- 全量重写已经放弃旧实现的一切，再背着 6 代迁移链是把旧包袱搬进新架构
- 五张表覆盖了全部必要状态：计划、任务、指纹、设置、站点规则
- 旧实现中的 `capture_sessions` / `media_groups` / `media_streams` 三表用于持久化浏览器候选——而候选的存活期只是一个标签页，扩展用内存存储即可，**不需要落桌面库**
- 不做迁移，升级回滚就不再需要"数据库也要回滚"的原子事务

## 后果

**正面**

- 消除三条 P1/P2 级别的风险（数据库回滚、迁移范围矛盾、迁移算法不确定性）
- schema 可以从"更干净"出发，而不是"兼容既有"
- 旧库原样保留给了用户兜底：想找回历史记录可以手动打开旧库

**负面（必须承认）**

- **覆盖升级后，用户在旧版本中的任务与站点规则不会出现在新版本中**。设置可以重新配置，历史任务记录只能靠旧库文件追溯。
- 若未来需要"从旧库导入记录"，得单独写一次性导入工具（当前**不在范围内**）。

## 替代方案

| 方案 | 否决理由 |
| --- | --- |
| 演进到 v7 并保留迁移链 | 把旧包袱搬进新架构，且引入数据库回滚事务的复杂度 |
| 全新库 + 一次性导入工具 | 可行，但导入工具本身需要理解旧 schema 与语义修复；当前判定收益不匹配（见"何时重新评估"） |
| 直接删除旧库 | 破坏用户数据，违背 B-401 的精神 |

## 何时重新评估

若用户明确反馈"希望保留旧版本的任务记录"，则**新增一份 ADR** 来定一次性导入工具的设计。在决策之前不为其写实现要求（当前不在范围内）。
