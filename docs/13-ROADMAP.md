# 13 · 实施路线

本文定义分阶段计划、每阶段的门禁，以及全部待确认项的解决时点。

---

## 1. 原则

| # | 原则 |
| --- | --- |
| 1 | **核心边界先定，细节 Just-in-Time**：架构与行为边界必须在编码前定；阶段内的实现细节在进入该阶段时再确认——只需解决**会阻塞当前阶段**的待确认项 |
| 2 | **每阶段可验证**：结束时要能演示，不是"写完了" |
| 3 | **契约对照**：每迁一块，先在 [11](11-ACCEPTANCE.md) 找到对应测试再实现 |
| 4 | **先测基线**：编码前测旧版本性能，作为对比基准 |
| 5 | **旧项目只读**：`E:\Users\MSI\Desktop\codex_download` 永不修改 |

## 2. 阶段总览：纵向功能切片

**每个阶段都产出一个可运行、可观察的东西**，而不是先把底层全建完、最后才接 UI。

| 阶段 | 名称 | 产出 | 能验证什么 |
| --- | --- | --- | --- |
| **0** | 规范编写 | 本套文档 | 用户检查 |
| **0.5** | 旧版基线 | 性能数据 | 有对比基准 |
| **1** | 可运行骨架 | App + SQLite + 基础 UI + 托盘 | 技术选型可行 |
| **2** | **第一条完整链路** | 扩展 → HTTP → Plan → 直链下载 → UI 实时进度 → 文件完成 | **端到端跑通** |
| **2.5** | **浏览器下载模式** | 弹窗开关 + 中转上传 + P6 落盘 | **拿不到链接时有退路** |
| **3** | 更多下载路径 | HLS / DASH / 分离音视频 / yt-dlp | 覆盖主要媒体类型 |
| **4** | Eagle 与 IDM | 导入链 + hook | 归档可用 |
| **5** | 视频号 | 捕获子系统 | 攻克难点 |
| **6** | UI 打磨 | 完整界面与主题 | 好看、流畅 |
| **7** | 安装与发布 | 安装器 + 手动更新 | 可分发 |
| **8** | 发布验证 | 发布验证文档 + M1~M13 逐项记录 | 可发布 |

### 2.1 为什么改成纵向切片

横向分层（数据 → 下载 → Eagle → 视频号 → UI）会让 UI 到第 6 阶段才完整出现，期间无法验证"用户到底能不能用"。

| # | 纵向切片的好处 |
| --- | --- |
| 1 | 阶段 2 就能看到"点一下，文件真的下载并出现在列表里" |
| 2 | 每阶段结束都能运行、能观察、能修，而不是攒几千行再集成 |
| 3 | 对 AI 辅助开发尤其重要——**写 → 跑 → 看 → 修** 的循环越短越好 |
| 4 | 早期暴露前后端接口设计问题，而这类问题最难返工 |

## 5. 阶段 2 · 第一条完整链路（最关键）

**产出**：**从浏览器点击到文件出现在磁盘上的完整通路**。

```text
浏览器页面
  → 扩展发现媒体、形成候选组、用户选择
  → HTTP API（Origin 白名单）
  → Service.CreatePlan
  → Media 下载直链（+ 进度）
  → 事件推送（200 ms 完整 PlanView）
  → UI 列表实时更新
  → FFprobe 校验
  → 文件落到「已完成」
  → Plan 状态 = completed
```

**这一阶段只做直链**（`media_kind = direct`），不碰 HLS / DASH / 页面解析 / 视频号。

| # | 交付物 |
| --- | --- |
| D1 | 本地 API：`/health`、`/api/plan`（创建 / 查询 / 停止 / 删除） |
| D2 | 扩展适配：删除配对与令牌逻辑，改为 Origin 直连；**列表按 P-101~P-110 重写** |
| D3 | `Service.PlanCreate` / `PlanStop` / `PlansList` |
| D4 | 直链下载 + 进度推送 |
| D5 | FFprobe 校验 |
| D6 | 下载页列表与详情（含实时进度） |

**门禁**：T-DL-01、T-DL-10、T-STB-01、T-EXT-10、T-EXT-15~19、T-FS-01。

**为什么列表重写必须在阶段 2**：阶段 6 的虚拟滚动只针对桌面端 UI。扩展列表的卡顿是旧版最突出的体验问题（每秒全量重建 DOM），且只能通过**改渲染模型**解决——它不是后期优化项，是架构选择。留到阶段 6 意味着阶段 2~5 的所有验收都跑在错误的渲染模型上。

**完成标志**：在真实浏览器点一次下载，文件出现在磁盘，界面进度实时更新。

## 9. 范围控制

**不在本次范围内**：

| # | 排除项 |
| --- | --- |
| O1 | 新增下载站点或平台（**适配器体系只规范组织方式，不扩大站点范围**；首批仅移植旧版已有的抖音与视频号） |
| O2 | 新增归档目标（Eagle 以外） |
| O3 | 云同步、账号体系 |
| O4 | 移动端 |
| O5 | 视频编辑或转码增强 |
| O6 | DRM 相关能力 |
| O7 | 对旧版本数据库的迁移 |
| O8 | 对旧 Python/C# 代码的兼容层 |
| O9 | 防攻击类安全机制（配对、令牌、威胁模型） |

> **浏览器下载模式不属于范围扩大**：它不新增站点、不新增下载路径，只切换「字节从哪来」（桌面端出站 ↔ 浏览器会话中转），落盘、合并、校验、交付与重试复用既有实现（[05 §4.4](05-DOWNLOAD.md)）。它是**唯一**为「同一链接桌面端拿不到」这一实际故障引入的新机制，符合设计原则 1。
