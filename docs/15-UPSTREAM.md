# 15 · 上游来源与第三方合规

本文登记**全部外部来源**：哪些代码被复用、哪些只用于研究、哪些以二进制随包分发，以及各自的许可证义务。

> **为什么单列一份**：旧实现这份信息散在 `UPSTREAM_PROVENANCE.md` 与 `COPYING.md` 里，而新项目的复用策略（[07](07-EXTENSION.md)）与发行边界（[10 §5.4](10-DISTRIBUTION.md)）都依赖它。**合规不是可选项**——漏登记一个上游就是侵权风险。

---

## 1. 三类来源，义务完全不同

| 类别 | 是否进入发行物 | 义务 |
| --- | --- | --- |
| **A. 复用代码** | **是** | 保留版权与许可证、提供对应源码、声明修改范围 |
| **B. 行为研究** | **否** | **一行代码都不能进**；只在文档里记"研究过什么、用于验证什么" |
| **C. 二进制工具** | **是**（随包分发） | 固定版本 + SHA-256、附许可证与第三方通知 |

**规则 R-1**：任何外部来源在进入本仓库前，必须先归入上表三类之一并在本文登记。**禁止**"先拿来用、以后再补文档"。

### 2.2 ⚠️ GPL-3.0 的传染性：这条路必须走完

**这是新项目必须正视的法律约束，不是技术选择。**

只要新项目**继续复用**含 cat-catch 代码的扩展，整个组合发行就必须满足 GPL-3.0：

| GPL-3.0 要求 | 对新项目的含义 |
| --- | --- |
| 分发即触发 | 只要把扩展交给用户（包括免费分发），义务就成立 |
| 必须提供**完整对应源码** | 扩展 JS 是运行必需品（[10 §5.3](10-DISTRIBUTION.md) 已说明它不属于"源码暴露"）——**必须可获取源码**，不能只发二进制 |
| 必须保留版权与许可证声明 | 不得移除上游版权头 |
| 必须声明修改 | 与 [07 §1](07-EXTENSION.md) 的"接口适配"改动对应，需逐项说明 |
| **衍生作品同样 GPL** | 不能把扩展改成专有许可 |

**因此**：新项目**不能**单方面把许可证改成 MIT 闭源分发。旧实现的组合发行就是 GPL-3.0（见 `COPYING.md`），新项目若要继承扩展源码，这条路必须走完。

**唯一能解除的路径**：扩展**完全重写**，不含任何 cat-catch 派生代码。那时才回到自由选择许可的状态。

### 2.3 决策：继续复用扩展（**已定**）

| 项 | 决定 |
| --- | --- |
| 路线 | **继续复用**含 cat-catch 代码的扩展（[07 §1](07-EXTENSION.md) 的适配路线） |
| 组合发行许可 | **GPL-3.0**，并按 §2.2 履行全部义务（固定上游源码、声明修改范围、保留版权、提供对应源码） |
| 用户给出的前提 | 用户明确：**本软件不出售**；一切优先功能，不为许可问题增加复杂度 |
| 决策日期 | 2026-10-02 |

**这个前提解决了什么、没解决什么**（必须分清，否则日后误判）：

| 议题 | 结论 |
| --- | --- |
| Commons Clause（§3.1 的 `ltaoo/wx_channels_download`） | **不构成约束**——该附加条款只禁止**销售**，本项目不出售，且该项目本来就属"行为研究"类、代码零复制 |
| GPL-3.0 的**分发**义务 | **仍然成立**。GPL 的义务由"分发"触发，与是否收钱无关——免费分发同样触发 |
| 因此仍然要做的事 | §2.2 表格的五行：保留上游源码与许可证、提供**完整对应源码**、保留版权声明、声明修改范围、不得改成专有许可 |
| 若将来改变定位 | **重新评估**。一旦转为对外公开分发（无论是否收费），"提供对应源码"的义务必须落实到位；若改为不公开的私人使用，则义务不被触发 |

> **不选另一条路的理由**：完全重写扩展的工作量与"适配"**差一个量级**（[13 §5](13-ROADMAP.md) 的扩展适配已是阶段 2 的门禁项之一），而收益只是许可自由度——在"不出售、优先功能"的前提下收益为零。

## 3. B 类：仅用于行为研究（**代码零复制**）

**规则 R-2**：B 类来源**不得**出现其代码、资源、构建产物、图标或 UI。研究与实现必须分离，而且**要在文档里写清"只用于验证什么"**——否则日后无从证明独立性。

### 3.1 `ltaoo/wx_channels_download`

- 来源：<https://github.com/ltaoo/wx_channels_download>
- 语言与许可证：**Go**，**MIT + Commons Clause**（该附加条款禁止销售）
- **用途**：研究用户可观察的微信视频号交互链路；**只读其行为与原理**
- **边界**：未复制、修改或分发其 Go/JavaScript、SunnyNet、Gopeed、证书、图标、UI、构建产物或 `WechatSphDecrypt` 源码
- 本项目的证书、回环代理、feed 规范化、候选、下载、流式处理与 UI **均按自身安全边界独立实现**
- 不是发行组件，不进入第三方组件清单

**它的架构与我们的相似**（证书 + 本机代理 + 页内注入下载按钮），因此它是一个**平行实现的可比对象**，研究价值在于"另一条路走通到哪一步"。

**从它读到的、已固化为本文档之外硬要求的内容**：

| 发现 | 落点 |
| --- | --- |
| 真实画质档位模型（`spec[]` 六个档位、外层另有更大的一组尺寸、`decodeKey`/`urlToken` 同响应配对） | [06 §6.6](06-WECHAT.md) |
| 原画档位是"合成"的（基础地址不加 `X-snsvideoflag`），且**当前被禁用**，精简 query 的尝试也被弃用 | [06 §6.6](06-WECHAT.md) |

> ⚠️ **Commons Clause 的含义**：它不允许"销售"本软件。本项目是**免费分发**的工具，但**若将来有任何收费/捆绑销售计划，这条必须先评估**——它是我们唯一遇到带此附加条款的参考项目。
>
> 另外：**不得**把它的代码片段、常量表或资源复制进本项目。研究结论以"事实与原理"的形式写入 [06](06-WECHAT.md)，而不是以代码形式。

### 3.2 `Evil0ctal/WeChat-Channels-Video-File-Decryption`

- 来源：<https://github.com/Evil0ctal/WeChat-Channels-Video-File-Decryption>
- **用途**：交叉核对两条公开实现方向——① 媒体 URL 与**同一响应中的** `decode_key` 必须配对；② ISAAC64 只处理文件**前 131072 字节**
- **边界**：未作为运行依赖，未复制进入发行载荷
- **重要限制**：该项目解决的是**取得 URL 与密钥之后**的文件解密，**不提供当前微信高清资产的签发接口**。因此它**不能**作为"高清下载已经完成"的依据（对应 [11 §5](11-ACCEPTANCE.md) 的 M5 仍未通过）

这三项是**阅读材料**，不是代码来源。它们**只用来确认技术方向**，不构成任何实现依赖，也不进入发行物。

### 3.4 ISAAC-64 的独立性

ISAAC-64 依据 **Bob Jenkins 的公共领域算法说明**独立实现，并以**公共领域测试向量**验证（[06 §8.1](06-WECHAT.md)、[11](11-ACCEPTANCE.md) `T-WX-17`）。

> 这条独立实现声明是合规的一部分：它使该算法的使用**不依赖** §3.1/§3.2 那两个项目。

### 4.1 yt-dlp 的站点覆盖 = 我们依赖的"全网支持"

**这是本项目覆盖面最大的一处外部能力，必须记清楚：**

| 项 | 值 |
| --- | --- |
| 站点提取器模块 | **约 934 个**（`yt_dlp/extractor/` 下 941 个 `.py`，扣除 `__init__` / `common` / `lazyloaders` / `adobepass` 等基础设施文件） |
| 覆盖范围 | 全网主流与大量小众站点，由上游持续维护 |
| 我们如何使用 | 以**固定版本的二进制**（`yt-dlp.exe`）做本机页面解析，不联网调用第三方服务，也不把其 Python 源码打进运行时 |
| 对应源码 | 随固定版本保存（`third_party/yt-dlp/`），满足合规 |

> **数字会随版本变化**：934 是 `2026.06.09` 固定版本的统计值。升级 yt-dlp 版本时必须重新统计并更新本行。

**由此推出三条架构结论**（也是 [02 B-305](02-BEHAVIOR.md) 与 [14](14-SITE-ADAPTERS.md) 存在的原因）：

| # | 结论 |
| --- | --- |
| 1 | **全网站覆盖靠 yt-dlp，不靠自己维护站点清单。** 项目**不得**再自建"支持站点列表"——那是重复建设，且永远追不上上游 |
| 2 | **站点适配器只做 yt-dlp 覆盖不到的那部分**（详见 §4.2） |
| 3 | **视频号是唯一没有上游解析器的站点**（§4.2），这是它难度量级完全不同的根本原因 |

### 4.2 yt-dlp 对中文平台的实际覆盖（已按源码核对）

`2026.06.09` 版本的实际情况：

| 平台 | yt-dlp | 提取器 |
| --- | --- | --- |
| **抖音** | ✅ **支持** | `tiktok.py` 内的 `DouyinIE`，规则 `https?://(?:www\.)?douyin\.com/video/(?P<id>[0-9]+)`，带实测用例 |
| **B 站** | ✅ 支持 | `bilibili.py`（普通视频、番剧、课程） |
| 小红书 / 西瓜视频 | ✅ 支持 | `xiaohongshu.py`、`ixigua.py` |
| 优酷 / 爱奇艺 / 微博 / 斗鱼 / 虎牙 / 腾讯 / 搜狐 | ✅ 支持 | 各自的提取器 |
| **视频号（微信）** | ❌ **完全不支持** | 941 个提取器里**没有** wechat / weixin / channels / finder / sph 任何一项 |

**这条决定了两个站点的性质完全不同**：

| | 抖音 | 视频号 |
| --- | --- | --- |
| 媒体地址解析 | **yt-dlp 已做**，我们不重复 | **无人可依**，必须自研 |
| 我们的适配器管什么 | **候选发现**（在页面上认出"这是哪个视频"）、画质档位、错误翻译 | 捕获（MITM）→ 身份绑定 → 解密 → 画质策略，**全链路自研** |
| 难度量级 | 低 | **最高**，且 M5 至今未通过 |

> **契约级的推论**：抖音适配器里的 `identity.urlRules` 与 yt-dlp 的 `_VALID_URL` **目标一致**（只匹配 `douyin.com/video/<数字>`）——这类规则**必须保持一致**，改一处就要改另一处（[14 A-104](14-SITE-ADAPTERS.md) 的唯一事实源原则在此要跨到上游）。凡是 yt-dlp 已经覆盖的站点，我们的规则**不得比它更宽**，否则会出现"我们认了但解析不了"的候选。
